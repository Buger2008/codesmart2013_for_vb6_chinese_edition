# 自动汉化循环 — 使用说明书

成品文件：`ahk_translate_loop.ahk`（AutoHotkey **v2**，单文件，无其它依赖文件）

---

## 一、它做什么

鼠标点进目标程序的文本框，按 `Ctrl+Alt+S` 开始，脚本就一个框一个框往下跑，`Esc` 随时停：

```
[取原文]  右键菜单键 -> a(全选) -> Ctrl+C
          -> translate.py            输出两行: 第1行 true/false, 第2行预处理后的文本
true  :   (全选) 粘贴第2行
          -> (全选) 等 400ms + 冲消息队列 + 等 300ms 给 STranslate 准备
          -> 右Alt+F 分步慢按 -> 等译文出现 -> 全选 Ctrl+C 取译文
          -> translateposthtml.py    输出一行 -> (全选) 粘贴回去 -> 回车
false :   直接回车
```

然后进入下一个文本框，无限循环。

## 四、配置速查（都在文件开头的「用户配置」段）

### 觉得"太快了 / 偶尔没触发"

| 配置 | 当前值 | 作用 |
|---|---|---|
| `T_TRANS_PREPARE` | **300** | 冲完消息队列后, 再给 STranslate 留的准备时间（**最常用**的旋钮） |
| `T_HOTKEY_HOLD_MOD` | 150 | RAlt 按下后等多久再按 F |
| `T_HOTKEY_HOLD_KEY` | 100 | F 按住多久 |
| `T_HOTKEY_HOLD_AFTER` | 150 | F 松开后等多久再松 RAlt |
| `SELECT_SETTLE_EXTRA` | 0 | 追加到"系统菜单延迟"之上 |
| `T_AFTER_ENTER` | 400 | 回车进下一个框后的**上限**（见第四·五节） |

### 全选 / 粘贴相关

| 配置 | 当前值 | 作用 |
|---|---|---|
| `SELECT_SETTLE_MODE` | `"system"` | 全选后等系统自己的菜单延迟(`SPI_GETMENUSHOWDELAY`=400ms)；写成数字则强制 |
| `VERIFY_SELECTION` | `true` | 全选后用 `EM_GETSEL` 问控件"真的全选了吗"，没全选就重来 |
| `SELECT_ALL_BEFORE_PASTE` | `true` | 每次粘贴前先全选（否则会插在光标处而不是替换整段） |
| `USE_MESSAGE_FLUSH` | `true` | 用 `WM_NULL` + `SendMessageTimeout` 确认目标程序处理完了按键 |
| `MENU_KEY` | `{AppsKey}` | 右键菜单键；不管用可换 `{F10}` 或 `+{F10}` |

### 翻译热键

| 配置 | 当前值 | 作用 |
|---|---|---|
| `TRANS_HOTKEY_MODE` | `"step"` | 分步慢按；改 `"string"` 就变回一次连发（老行为） |
| `TRANS_HOTKEY` | `{RAlt down}{f down}{f up}{RAlt up}` | 热键本体（`"string"` 模式用） |
| `TRANS_RETRY` | 1 | 等完没反应就重来几遍 |

### 翻译不响应时的止损

列表里经常有**几十行内容一模一样**（比如同一个占位说明），旧版日志里"同一个框连续读 10 几次"是常态。如果这些行都要翻译、而 STranslate 又不响应，那**每条要花 12s + 重试 12s ≈ 30 秒**，几十行就是十几分钟 —— 看起来就像"卡在这个框上无限循环"。

| 配置 | 当前值 | 作用 |
|---|---|---|
| `SKIP_KNOWN_FAILED` | `true` | 某个文本本会话里翻译失败过，再遇到就**跳过翻译只回车**（30s → 1s）。每次重新按 Ctrl+Alt+S 会清空这个记录，方便你修好 STranslate 后重试 |
| `SKIP_TRANS_PATTERN` | `^<[^<>]*>$` | **翻译器根本不处理的文本**：整串被一对尖括号包起来、里面没有别的尖括号（如 `<Click on a list item to see a brief problem description here>`）。这类 STranslate 会**原样返回**，脚本等满 12s 再重试 12s 也永远等不到变化 —— 直接当"不需要翻译"跳过。留空 = 不启用 |
| `MAX_TRANS_FAILS` | 3 | 连续这么多次翻译**完全没反应**就停下弹框报警（说明 STranslate 根本没工作，再跑下去只是白等）。`0` = 不检查 |

> ⚠ `SKIP_TRANS_PATTERN` 别写成 `^<.*>$` —— 那会把 `<strong>File</strong>` 这种真该翻译的也跳过。自检里有一条专门检查这个（跳 `<...>` = 是，跳 `<strong>File</strong>` = 否）。

### 等待译文

| 配置 | 当前值 | 作用 |
|---|---|---|
| `WAIT_MODE` | `"poll"` | 轮询看文本变没变；改 `"fixed"` 变成死等 `T_TRANS_FIXED` |
| `T_TRANS_WAIT` | 1200 | 按完热键先干等多久再开始看（**想再快就降到 300**，见第四·六节） |
| `T_TRANS_POLL` | 500 | 每隔多久看一次 |
| `T_TRANS_MAX` | **2500** | 等"**第一次出现变化**"的上限；超了就判定 STranslate 没反应，不再干等 |
| `T_TRANS_GRACE` | 3000 | **一旦已经看到变化**，再多给这么久确认稳定 —— 防止刚好卡在 2.5s 边界出现的译文被丢掉后又被原文覆盖 |
| `T_PY_MAX` | 60000 | 单次 python 调用上限（judge 联网最坏 34s） |

### 其它

| 配置 | 当前值 | 作用 |
|---|---|---|
| `USE_API_SELECT` | **`false`** | 全选是否先试 Windows API `EM_SETSEL`。**实测不可用**（高亮了但 Ctrl+C 复制不出来），见第四·八节 |
| `ADAPTIVE_WAITS` | `false` | 自适应等待总开关（**默认关**：开着那次翻译全不响应，见第四·五节） |
| `SEND_MODE` | `"Event"` | 像真人按键，兼容老程序；嫌慢改 `"Input"` |
| `KEY_DELAY` / `KEY_DUR` | 30 / 20 | 按键间隔 / 按住时长 |
| `T_MENU_OPEN` / `T_MENU_PICK` | 300 / 200 | 等菜单弹出 / 按完 a —— **这两个别动**，动过就翻译失效 |
| `T_AFTER_ENTER` | **0** | 回车后不等，立刻取文本（取文本自己还有约 500ms 菜单时间，够程序把下一个框填好） |
| `T_AFTER_PASTE` | **0** | 粘贴后不等，直接回车 |
| `T_AFTER_COPY` | **0** | Ctrl+C 之后不等；`ClipWait` 已确认剪贴板有内容 |
| `T_CLIP_WAIT` | **600** | 等剪贴板出现内容的上限（取文本是本地操作，不该等 2 秒） |
| `SHOW_STATUS` | `true` | 右上角显示"运行中 #n" |
| `DEBUG_LOG` | `true` | 写日志 |

## 四·五、时间花在哪 / 那次"优化"的教训

### 实测：时间都花在固定等待上（python 不是瓶颈）

| 阶段 | 平均耗时 | 性质 |
|---|---|---|
| 取文本（菜单全选 + Ctrl+C） | **0.86s** | 固定 Sleep 300+200+150 |
| 回车 → 下一个框 | 0.48s | 固定 Sleep 400 |
| **不需要翻译的条目，合计** | **1.62s** | |
| python 调用 | 0.28s | 其中 `import requests` 就占 0.3s（judge 的依赖）|
| 翻译条目额外：粘贴 + 取基准 | 2.00s | 两次菜单全选 |
| 翻译条目额外：全选 + 确认 | 1.00s | settle 400 + prepare 300 |
| 翻译条目额外：等译文 | 4.00s | 含 STranslate 自己的耗时 |

### 试过一次自适应等待，翻译全不响应，已回退

思路是"能确认就提前走，确认不了才等满上限"（看菜单窗口 `#32768`、看焦点换控件、`WM_NULL` 冲队列）。结果：

- ✅ 取文本 0.86s → **0.171s**，不需要翻译的条目 1.62s → **0.81s**
- ❌ **需要翻译的条目连续 4 次全部不响应**（每次等 8 秒你按 Esc）

怀疑点：**"菜单窗口出现" ≠ "菜单能接受加速键"**。按 `a` 按得太早，可能根本没触发"全选"，于是 STranslate 拿不到选中内容；而取文本/粘贴两条路对这个不敏感（这个控件的 `Ctrl+C`/`Ctrl+V` 不依赖选中），所以**只有翻译会坏，日志看着还正常**。

因此现在默认 `ADAPTIVE_WAITS := false`（死等，即跑出 240 次翻译成功的那版参数）。想再试就在**单条文本**上试，盯日志里 `[取文本]` / `[等译文]` 的耗时，别整轮跑。

### 另外两件事（都不是原因，但别被误导）

1. **`EM_GETSEL` 全选核对对这个控件无效**（现在默认关）。旧版日志里同样是 `选中 37..0 / 共 37 字符`，可它成功了 240 次 —— 说明这控件无论选没选中都报成"空"。它报的"没全选"是假信号。
2. **`SPI_GETFOREGROUNDLOCKTIMEOUT` 昨天是 0，今天是 2147483647**。这个值是"用户输入后，系统多久内不许别的程序抢前台"。STranslate 如果要激活自己的窗口，这个值可能会影响它 —— 如果回退后**仍然**不响应，优先查这个（注册表 `HKCU\Control Panel\Desktop\ForegroundLockTimeout`）。

### 关于"在同一个框上无限循环"

先分清两种：

| 现象 | 真相 |
|---|---|
| 连续读同一个内容十几次、但每条只花约 1 秒 | **正常**。列表里多行内容相同，旧版也这样，它最终会走过去 |
| 卡在同一个内容上，每条要 30 秒 | 那个文本要翻译、而 STranslate 不响应 → 每条都白等 12s+12s。现在有 `SKIP_KNOWN_FAILED` 止损，第 2 次遇到同文本就 1 秒跳过 |

⚠ **不要**加"内容重复就停止"的保护 —— 历史日志里 881 条中有 81 条相邻重复，那是这个程序的正常形态，加了会误杀。

## 四·六、2026-10-06 等待压缩（实测 10.3s → 约 8.9s）

按实测日志把"该快的步骤"压掉（每个值都能单独改回来）：

| 阶段 | 改前 | 改后 | 怎么改的 |
|---|---|---|---|
| 取文本 | 828ms | **~678ms** | `T_AFTER_COPY` 150→0（`ClipWait` 已经同步过） |
| 空文本框 | 2000ms | **600ms** | `T_CLIP_WAIT` 2000→600（本地操作，不该等 2 秒） |
| 粘贴预处理文本 | 1297ms | **~1147ms** | `T_AFTER_PASTE` 150→0 |
| 粘回译文 | 1304ms | **~1154ms** | 同上 |
| 回车+等下一个框 | 453ms | **0ms** | `T_AFTER_ENTER` 400→0（取文本自己有约 500ms 菜单时间兜底） |
| 等译文（正常） | 3.38s | **~3.06s** | 轮询本身变快（`T_AFTER_COPY`=0） |
| **等译文（没反应）** | **12s + 重试 12s** | **2.5s + 重试 2.5s** | `T_TRANS_MAX` 12000→2500 |

一轮合计：**不需要翻译 1.48s → 约 0.87s**；**需要翻译 10.28s → 约 8.9s**。

新增 `T_TRANS_GRACE`（默认 3000ms）：`T_TRANS_MAX` 只管"**第一次出现变化**"的上限；一旦已经看到变化，就再给 3 秒确认稳定 —— 否则刚好卡在 2.5s 边界出现的译文会被判失败，然后被原文覆盖，那才是真的亏。

**下一个候选（这次没动）**：`T_TRANS_WAIT` 1200 → 300。
现在第一次轮询要等 1200+678 ≈ **1.88s** 才发生，所以"翻译器 1.9 秒内没返回"就会先被判失败（靠 `T_TRANS_GRACE` 兜回来，但总时长变成 ~4.2s）；降到 300 后第一次轮询在 ~0.98s，正常翻译的等待能从 3.06s 降到 **约 2.2s**。代价是翻译器工作期间多弹一次菜单（可能打扰它，需要单条验证）。

## 四·七、全选探针（Ctrl+Alt+P）：能不能不用右键菜单全选？

**为什么要测**：每弹一次右键菜单全选要等 `T_MENU_OPEN`(300) + `T_MENU_PICK`(200) = **500ms**，而一条要翻译的文本要全选 **5 次**（取文本 / 粘贴 / 取基准 / 全选确认 / 粘回），光菜单就 **2.5 秒**。

**怀疑点**：日志里全选后的 `EM_GETSEL` 读数是 `37..0`（37 字符文本）和 `6..0`（6 字符文本）。按手册"低16位=起点、高16位=终点"读，这是"起点在末尾、终点为 0"—— 一个**反向的全选**，而不是"没选中"。旧版报 `37..0` 却成功翻译 240 次，正好印证这一点。

**如果它是标准 Edit 控件（VB6 文本框就是），`EM_SETSEL` 就能直接全选**：纯消息、不弹菜单、不依赖时序，每次约 1ms。

### 怎么用

1. 鼠标点进目标程序的那个文本框
2. 按 **`Ctrl+Alt+P`**
3. **看文本框有没有整段高亮**
   - **有高亮** → API 可用，可以接进流程
   - **没高亮** → API 不可用，继续用右键菜单

不弹窗。探针会先按一下 `→` 把选中收起来（只动光标、不改文本），再发 `EM_SETSEL(0,-1)`，这样"全选前 / 全选后"一眼可辨。两次读数都写进日志（`探针(API全选) ...`），便于复核。

> 循环运行中按 `Ctrl+Alt+P` 不会执行（会打乱流程），只会提示先按 Esc。

### 实测结论（2026-10-06）

- **`EM_SETSEL` 有效** ✅ —— 目视确认：按 `Ctrl+Alt+P` 后文本框**整段高亮**。
- **`EM_GETSEL` 是常数桩** ❌ —— 三种状态的读数**完全一样**：

  | 状态 | 读数 |
  |---|---|
  | 按 `→` 收起选中（肯定没选中） | `10..0 / 共 10 字符` |
  | `EM_SETSEL` 全选之后 | `10..0 / 共 10 字符` |
  | 右键菜单全选之后 | `10..0 / 共 10 字符` |

  所以它既不反映"反向全选"，也不反映任何选中状态 —— **这个控件不上报选中范围**，`EM_SETSEL` 的效果**没法自动核对**，只能靠目视。防线是 `USE_API_SELECT` 一键关掉 + 翻译连续失败自动停下报警。

> 顺带纠正一段历史误判：早先日志里那个 `37..0` 被我当成"反向全选"，其实只是这个常数桩的输出。它既不能证明全选成功，也不能证明失败。

## 四·八、试过"全选改走 Windows API"，**已退回**（2026-10-06）

思路：`EM_SETSEL(0,-1)` 是纯消息，约 1ms、不弹菜单，比右键菜单每次省 500ms。

**探针目视结果**：按 `Ctrl+Alt+P` 后文本框**确实整段高亮** ✅

**但接进流程后立刻出问题** ❌ —— 日志：

```
15:14:43  ★ 全选改用 Windows API (EM_SETSEL)
15:14:44  没取到文本 (空文本框或复制失败)  [取文本 718ms]
15:14:44  没取到文本 (空文本框或复制失败)  [取文本 703ms]
15:14:45  没取到文本 (空文本框或复制失败)  [取文本 688ms]
15:14:49  原文: "&Export >>"  [取文本 78ms]        ← 偶尔成功
15:17:21  没取到文本 ... [688ms] ×3
```

**9 次取文本里 8 次读不到**（688ms = 剪贴板 600ms 超时；正常只要 ~78ms），而 API 一次都没报"发送失败"。

**结论：`EM_SETSEL` 只让文本框"看起来选中了"，但之后 `Ctrl+C` 复制不出内容。**
推测这个 VB 控件的高亮（Edit 层状态）和它"可复制的选区"（VB 层状态）不是同一份 —— 只有**走右键菜单那条路**才会把 VB 层的选区也更新掉，所以只有它能让 Ctrl+C / STranslate 拿到内容。

所以 `USE_API_SELECT` 默认 **`false`**（回到右键菜单）。代码留着，想再验证可以打开，但要盯日志里的"没取到文本"。

> 这一条同时也解释了之前那个疑问：为什么"菜单全选"看起来又慢又土、却一直能用 —— 因为它是**唯一**能同时满足"高亮 + 可复制"的方式。

## 四·九、热键（以及一次"热键全废"的事故）

热键写在**文件末尾**，用的是**静态定义**：

```ahk
^!s::RunLoop()              ; 开始 / 停止循环
^!+p::ProbeSelectAll()      ; 全选探针 (Ctrl+Alt+Shift+P)

#HotIf running
Esc::StopLoop()             ; 运行中按 Esc 停止
```

### ⚠ 为什么不用 `Hotkey()` 动态注册

2026-10-06 我为了"让热键可配置"，改成用 `Hotkey()` 注册，结果：

```
!! 热键注册失败: ^!s -> Invalid callback function.
!! 热键注册失败: ^!+p -> Invalid callback function.
```

**两个热键全没注册上，按下去毫无反应。** 实测（AHK 2.0.29）各种写法：

| 写法 | 结果 |
|---|---|
| `Hotkey(key, (*) => ...)` 匿名箭头函数 | ✅ 唯一可用 |
| `Hotkey(key, 裸函数名)` | ❌ Invalid callback function |
| `Hotkey(key, 变量持函数引用)` | ❌ Invalid callback function |
| `Hotkey(key, Func("名字"))` | ❌ Invalid base |
| `Hotkey(key, "名字")` | ❌ Parameter #2 of Hotkey is invalid |

**这个版本里命名函数引用传不进去。** 所以热键一律用静态定义 —— 还有个额外好处：写错了在**加载时**就报错，不会等到运行时才发现。

> 自检里加了一条回归检查，专门验证"`Hotkey()` 只接受匿名箭头函数"这件事，并记录上面这张表，免得以后再踩。

### 如果怀疑和 STranslate 撞车

先看现象：**按脚本热键时，翻译软件也被触发了**（比如弹出它自己的菜单）。
排查方法：把 `^!s` 临时换成 `^!+s`（多一个 Shift）再试 —— 如果不再触发，就是撞车，换组合即可。

## 五、日志里怎么定位问题

| 日志行 | 含义 / 对策 |
|---|---|
| `第 N 个文本框 (上一轮共 4.2s)` | **一整轮的总耗时** —— 看优化效果就看这个 |
| `[取文本 250ms]` `[python 280ms]` `[回车+等下一个框 120ms]` `[等译文 3.5s]` | 各阶段实测耗时，用来找瓶颈 |
| `原文: "..."` | 取到的原文。是空的话看下一个框 |
| `translate.py -> need=true/false` | 第1行判定 + 第2行预处理文本 |
| `翻译前基准: "..."` | 粘贴后从盒子读回来的规范文本，**应该和上面 `text=` 一致** |
| `全选核对(...): 选中 0..78 / 共 78 字符` | 真的全选了 ✅（**这个控件不上报真实范围，默认已关**，见第四·五节） |
| `控件不响应 EM_GETSEL, 跳过核对` | 文本框是自绘控件，核不了 |
| `按翻译热键 (第 1 次, step 模式)` | 热键发出去了 |
| `译文已稳定 (轮询 5 次)` | 抓到译文了 ✅ |
| `第 N 次轮询看到内容变了` | 译文开始出现 |
| `等译文超时(12000ms), 轮询了 20 次, 内容一次都没变 -> 判定 STranslate 没反应` | **关键证据**：说明 STranslate 完全没动（不是脚本没看到） |
| `!! 文本框没有任何变化, 判定这次没翻译成功` | 同上，会自动重试 |
| `已按 Esc, 中止本次调用` | 是你自己按停的，不是错误 |
| `冲消息队列超时/失败` | 目标程序卡住，退化成了纯等待 |

## 六、已知限制

- 脚本只发按键，**不管鼠标**；跑的过程中别去点别的窗口，否则按键会打到别处
- 目标文本框如果是自绘控件（不响应 `EM_GETSEL`），"全选是否生效"无法核对，只能靠重试
- `translate.py` 的 judge 会联网，最坏 34 秒；这段时间脚本在等，按 `Esc` 可以中断
- 出错会弹一次对话框并停止循环；按 `Esc` 中断不会弹
